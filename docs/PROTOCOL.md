# Протокол Smoant Pasito III (S052) — что подтверждено живьём

Всё ниже снято 2026-11-18 с реального устройства `41:42:FD:6A:53:2B` (имя `LE-S052`),
спаренного с Linux/BlueZ 5.87. Где это догадка — так и написано.

## Реклама (advertising)

| Поле | Значение |
|---|---|
| Local name | `LE-S052` |
| Flags | `06` (LE General Discoverable, BR/EDR not supported) |
| Manufacturer data | company ID `0x0642` = **Bluetrum Technology**, значение `02 02 00 ec ef 50 c7 fe 86 00 00 00 00` (13 байт; полный blob 15 байт: `42 06 02 02 00 ec ef 50 c7 fe 86 00 00 00 00`) |
| Service data `00003802-0000-1000-8000-00805f9b34fb` | **собственный MAC устройства** (`41 42 fd 6a 53 2b`) |
| UUIDs | `6e400001-b5a3-f393-e0a9-e50e24dcca9d` (vendor), `00003802-…` |

`00003802` — кастомный 16-битный UUID: в списке SIG его нет, отдельного GATT-сервиса за ним не
наблюдается, это только метка в рекламе (перенос MAC).

Кандидат Pasito определяется по трём независимым признакам: UUID сервиса, имя `LE-S052`,
manufacturer data с префиксом `42 06 02 02 00` длиной 15 байт.

## GATT

Один первичный сервис (handle 0x0001):

| Handle | Характеристика | Свойства | Роль |
|---|---|---|---|
| 0x0002 | `6e400003-…-CCA9D` | notify (+ CCCD 0x0004) | поток кадров устройства → клиент |
| 0x0005 | `6e400002-…-CCA9D` | write-without-response | записи клиента (пока не расшифрованы) |
| 0x0007 | `6e400004-…-CCA9D` | read, write | **буфер 512 байт**: чтение/запись конфигурации |

Сервиса Nordic DFU (`0xFE59`), OTA-сервиса, файлового канала и вторых vendor-сервисов нет.
По совокупности (Bluetrum + отсутствие DFU-сервиса) штатного обновления прошивки через BLE,
скорее всего, не существует.

## Формат кадра notify `6e400003`

```
[seq:u8][msg:u16 LE][flags:u8][declared_len:u8][payload: declared_len байт]
```

- `seq` — сквозной счётчик сообщений устройства (mod 256); за одну сессию расходуется 3 значения.
- `msg` — id сообщения. Наблюдены: `0x035c`, `0x0351`, `0x0370`.
- `flags` — во всех наблюдениях `0x00`.
- `declared_len` — длина payload; у большого кадра она больше фактически принятого.

Реальный захват (seq=0x0a, сессия «подписка + чтение 0004»):

```
0a 5c 03 00 1d 00 3f 5c 37 04 57 5f 00 00 3f 00 00 00 ff ff 1f 00 32 2a 00 00 ff 0f 00 00
0b 51 03 00 02 00 00
0c 70 03 00 04 01 18 b4 41
```

| Кадр | msg | declared_len | payload (факт) | Повторяемость |
|---|---|---|---|---|
| state | `0x035c` | 29 | 25 | байт-в-байт одинаков между сессиями |
| mode | `0x0351` | 2 | 2 | `00 00` |
| dvw | `0x0370` | 4 | 4 | `01 18 b4 41` |

Большой кадр приходит усечённым: 30 байт всего = 5 байт заголовка + 25 payload, при
`declared_len = 29`. Значит ATT MTU = 33 (максимум notify = MTU−3 = 30), и 4 байта хвоста
не доставляются (фрагментации/продолжения не наблюдалось). Семантика полей payload **не
расшифрована**; гипотезы: батарея/ватты/сопротивление/счётчик затяжек.

## Буфер `6e400004` (512 байт)

Чтение возвращает 512 байт. Первые байты менялись между сессиями (`00 00…`, `01 00…`, `01 01…`)
— похоже на статус/эхо предыдущей операции. Запись `01 00` → чтение вернуло `01` (значение
сокращается до записанного), запись `01` → чтение вернуло `01`.

Кадр DVW-профиля: **`02` + 10 байт**, один байт на ступень, значение ≈ ватты (5–100 Вт).
Наблюдение из macOS-репозитория: `0x4b` = 75 Вт, `0x4c` = 76 Вт. Кодирование допускает 0..255,
но устройство физически 5–100 Вт.

## Жизненный цикл сессии

1. Клиент подключается (bonded/trusted, адрес в BlueZ — RPA `41:42:FD:6A:53:2B`).
2. Подписка на `0003` → в течение ~50 мс приходят три кадра (state/mode/dvw).
3. Простой: устройство само разрывает связь через **~13 с** (remote user), если ничего не делать.
4. Чтение/запись `0004` → устройство закрывает сессию ещё быстрее (~4 с после операции).
5. После разрыва устройство снова рекламируется `LE-S052`; клиент может переподключиться.

Выводы для софта: держать переподключение, не считать разрыв ошибкой, не читать `0004`
без необходимости (чтение завершает сессию).

## Что НЕ подтверждено (открытые вопросы)

1. Семантика полей кадра `0x035c` (нужна корреляция с показаниями экрана: ватты, режим,
   заряд %, Ом, счётчик затяжек).
2. Что означает `0x0370` (`01 18 b4 41`): возможно, DVW-профиль или его часть.
3. Порядок «приёма передачи»: в macOS-репозитории описано `подписка → 01 00 → чтение`,
   но роль отправителя/получателя в Share до конца не ясна.
4. Применяется ли записанный профиль `02+10` на устройстве (ATT-ack ≠ применение).
5. Существуют ли другие опкоды (темы/калибровка/статистика) — проверяется осторожным перебором.

## План экспериментов

1. **Корреляция**: снять кадры, когда на экране известны ватты/режим/заряд/Ом/затяжки; затем
   изменить по одному параметру и сравнить payload — так декодируются поля `0x035c`.
2. **DVW**: записать `02+10` с заведомо отличимой кривой (например, плоские 30 Вт), прочитать
   `0004` обратно (ожидаем эхо `02 1e …`), проверить экран устройства.
3. **Share**: перевести Pasito в режим передачи профиля и принять его на ПК (эмулятор
   периферии на BlueZ — `GattManager1`/`LEAdvertisingManager1` доступны без экспериментального
   флага).
4. **Опкоды**: перебирать `00..ff` в `0004`/`0002` по одному, фиксируя ответы в журнале; любые
   записи, меняющие поведение, документировать.

## Риски

- Запись неизвестных опкодов в `0004` может изменить настройки устройства; начинать с
  документированных `01 00` и `02+10`, значения мощности держать в 5–100 Вт.
- ATT-подтверждение не означает применение на устройстве — проверять экран.
- Эксперименты только со своим устройством.
